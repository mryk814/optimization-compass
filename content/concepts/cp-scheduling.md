機械が1単位時間空く予定は、詰め方が悪いのでしょうか。必ずしもそうではありません。材料が届く前には始められない作業があると、避けられない空白を含む予定でも、全作業を最も早く終えられます。

ここでは、1台の機械と3作業だけで「実行できる」「これ以上早くできない」を別々に確かめます。順序を変えると、終了は8、7、10。最適な7の予定にも空白が1あります。

## 30秒でつかむ

制約プログラミングによるスケジューリングは、開始時刻、先行関係、資源の競合を制約として表す定式化です。

- **決めるもの**: 各作業の開始時刻。1台の機械では、重ならない順序も決まる
- **良くしたいもの**: 最後の作業の終了時刻。この目的をメイクスパンと呼ぶ
- **守ること**: 材料が届く時刻、先に終える作業、機械の同時使用禁止

[教室の時間割](#/gallery/course-timetabling)や[勤務シフト](#/gallery/shift-scheduling)も、競合と割当を直接表す場面です。ただし「終了を早める」以外に、希望違反や公平性を目的にすることもあります。本稿の稼働率を、スケジューリング一般の良さの尺度にはしません。

## 標準形を読む

作業が占める区間を重ねず、必要な順序と資源の条件を守って、最後の終了を早めます。

$$
\min_s C_{\max},\qquad C_{\max}=\max_i(s_i+p_i)
$$

$$
\operatorname{NoOverlap}(\{[s_i,s_i+p_i)\}),\qquad
s_j\ge s_i+p_i\quad ((i,j)\in E),\qquad s_i\ge r_i
$$

| 記号 | 意味 |
|---|---|
| $s_i$ | 作業 $i$ の開始時刻 |
| $p_i$ | 作業の所要時間 |
| $r_i$ | 作業を開始できる最早時刻 |
| $E$ | 先に終える必要がある作業の組 |
| $C_{\max}$ | 全作業の終了時刻 |

`NoOverlap` は、同じ機械を使う作業の区間どうしが重ならないという条件です。
終了時刻と次の開始時刻が同じ場合は、半開区間なので重なりません。
機械が複数ある場合は、機械ごとに競合する区間をまとめます。

人数や電力など容量を共有する資源には、同時使用量の合計を容量以内にする条件を使います。
「時間が重ならない」と「重なっても合計が容量以内」は異なる条件です。
一つの `NoOverlap` にすべての作業を入れると、別の機械で動ける作業まで直列化してしまいます。

## 小さな例

作業Aの所要時間は2、Bは3、Cは1とします。
Bは時刻4に材料が届くので、それより前には始められません。
CはAが終わった後に始めます。
作業の中断は認めず、一台の機械を共有します。

| 作業 | 所要時間 | 開始できる最早時刻 | 先行条件 |
|---|---:|---:|---|
| A | 2 | 0 | なし |
| B | 3 | 4 | なし |
| C | 1 | 0 | Aが終了している |

### 一手を追う：Bを待つ前にCを入れる

Aを時刻0に始めると2に終わります。次をBに固定すると、開始は $\max(2,4)=4$。Bが7に終わるまでCを入れられず、全終了は8です。

一方、次をCにすると、A終了後の時刻2から3まで処理できます。その後のBは $\max(3,4)=4$ に始まり、7に終わります。変えたのは所要時間でも材料の到着時刻でもなく、**待つ前に何を済ませるか**です。


AがCより先になる順序を列挙し、それぞれ最も早く開始させた結果です。

| 順序 | Aの開始 | Bの開始 | Cの開始 | 全終了 |
|---|---:|---:|---:|---:|
| A → B → C | 0 | 4 | 7 | 8 |
| A → C → B | 0 | 4 | 2 | 7 |
| B → A → C | 7 | 4 | 9 | 10 |

![同じ3作業についてA B C、A C B、B A Cの順序を最早開始させたガント図。終了は8、7、10。Bの開始可能時刻4と終了下界7を点線で示す。](./media/cp-scheduling-order-oracle.svg "全順序のうちAがCより先の3通りを描画。これは全列挙による教材で、CP-SAT内部の探索履歴ではありません。")

図は横軸が時刻、色の長さが所要時間です。中央の行の3〜4が空白でも、右端は最も左にあります。時刻4の縦線はBの開始可能時刻、時刻7の縦線はどの予定も越えて早く終われない下界です。

AとCを先に済ませると、材料が届くまでの時間を利用できます。
時刻3から4には機械を使わない時間が残ります。
それでも終了時刻7は最適です。
Bは時刻4より前に始められず、所要時間が3なので、どの予定も7より前には終われません。

最早開始を使う理由も確認します。固定した順序では、次の作業の開始は「直前の終了」と「その作業の開始可能時刻」の大きい方です。これより遅らせても、後続を早く始められるようにはなりません。この固定所要時間・単一機械・中断なし・メイクスパン最小化という条件なら、各順序の最早開始だけを比べれば足ります。遅らせると報酬が上がる目的や、段取り時間が時刻で変わるモデルまで、この議論を流用しません。

これは実行可能な予定と、最適値の下界が一致した例です。
実行可能な予定が一つ見つかっただけなら、その一致までは確認できません。

## 見分け方

「同じ機械を同時に使えない」「この工程の後で始める」「この時間だけ人が必要」という条件が手がかりです。
時間区間と順序を、そのまま制約として扱えるかを確認します。
制約の種類によっては、割当を先に決めてから開始時刻を決めます。

作業の所要時間が状態や操作の連続関数として変わるなら、[一般制約付きNLP](#/formulations/PA009)も検討します。
輸送経路と移動順序が主な決定なら、[配送経路](#/formulations/PA031)の構造も必要です。
時間割という呼び名だけで、すべてが同じ定式化になるわけではありません。

## 近い定式化

開始時刻を離散化するか、作業順序を0-1変数と大きな定数で表すと、[混合整数線形計画](#/formulations/PA023)へ書き換えられる場合があります。
時間の離散化では、単位を細かくするほど変数や制約が増えます。
大きな定数を使う場合は、開始時刻の範囲から妥当な値を決めます。

制約プログラミングでは、区間の競合などをまとまりのある制約として記述できます。
MILPでは、線形の費用やほかの連続変数との結び付きが自然な場合があります。
条件の表しやすさと、得られる下界の情報を、同じ問題で比較します。

## 解き方の系統

[制約プログラミング探索](#/learn/cp-search)は、変数の候補を制約で絞り、残った選択肢を分岐して調べます。
[CP-SAT](#/learn/cp-sat)では、整数の開始時刻と区間を使ったモデルが入口になります。
作業区間の作り方と競合の記述は、[OR-Toolsの公式例](https://developers.google.com/optimization/scheduling/job_shop)で確認できます。

次のPython例は、三つの作業に限って順序を全列挙します。
所要時間と開始可能時刻が固定され、先行関係がAからCだけなので、各順序を最早開始させれば確かめられます。

```python
from itertools import permutations

duration = {'A': 2, 'B': 3, 'C': 1}
release = {'A': 0, 'B': 4, 'C': 0}
answers = []
for order in permutations(duration):
    if order.index('A') > order.index('C'):
        continue
    starts = {}
    clock = 0
    for task in order:
        clock = max(clock, release[task])
        starts[task] = clock
        clock += duration[task]
    answers.append((clock, order, starts))
for answer in answers:
    print(answer)
```

終了時刻は順に8、7、10となります。
最小の7を選べば、図の中央行を再現できます。コードが調べるのは開始時刻の全組合せではなく、6通りの順序から先行条件に合わない3通りを除いたものです。各順序は最早開始で代表させています。

この全列挙は、小さなモデルの答えを照合するための基準計算（oracle）です。制約伝播やSAT学習を使うCP-SATそのものではありません。作業が増えた実問題でCP-SATを使うなら、得た開始時刻を元の条件へ戻して検査し、終了状態と最良下界も別に読みます。
順序の全列挙は作業数に対して急増するので、大きな予定表には専用の探索を使います。

MILPへ書き換えた場合は、[branch-and-cut](#/learn/branch-and-cut)の系統が候補です。
局所探索を使う場合は、予定の改善と最適性の証明を分けて扱います。
どの系統でも停止時の実行可能性を確認します。
目的値と下界と、その差も記録します。本例の目的値は7、下界も7なので差は0です。終了8の予定だけを得た段階では、下界7との差1が残り、まだ最適とは呼べません。

## つまずきやすい点

時間の単位を整数へ変えるときは、作業時間と開始可能時刻を同じ単位にします。
丸めて作業を短くすると、実際には重なる予定を作る可能性があります。
変換前の単位でも、終了時刻と資源使用量を再計算します。

条件が両立しないときは、探索を長くする前に、先行関係の循環や資源の容量を調べます。
必須条件と希望条件を分けることも必要です。
希望をすべて必須にすると、利用できる予定が消える場合があります。

時間制限で終了した結果は、予定があるかを先に確認します。
実行可能解がある場合も、最適性の証明が終了したとは限りません。
下界との差が残るなら、追加探索で改善または証明する余地を示しています。

## 自分で一つ変える

Bの開始可能時刻を4から2へ変えると、A→B→CとA→C→Bはどちらも6で終わります。所要時間の合計が $2+3+1=6$ なので、今度は機械の総仕事量が下界になり、空白のない予定が最適です。「空白があるか」だけではなく、どの制約が最も強い下界を作っているかを読み取ってください。

区間・先行・同一機械の競合のモデル化は[OR-Tools公式のJob Shop例](https://developers.google.com/optimization/scheduling/job_shop)、終了状態の意味は[CP-SAT公式説明](https://developers.google.com/optimization/cp/cp_solver)で確認できます。ここで実行したPythonは標準ライブラリの全順序列挙です。
