# Shift scheduling: preference tie-break journey

- Status: implementation brief
- Date: 2026-07-26
- Scope: `shift-scheduling` only
- Related canonical Case: `shift-scheduling` (`PA026`)

## Why this journey is needed

`shift-scheduling` is the only published Gallery Case without a comparison. Its current visualization
is the general problem-structure Map, so a reader cannot see an actual schedule or distinguish hard
coverage rules from a soft preference objective.

The fixed lesson will compare two schedules produced from the same complete enumeration:

1. maximize fulfilled requests, then keep the first deterministic tie;
2. maximize the same requests, then minimize the staff workload range as a secondary tie-break.

Both schedules satisfy the same hard constraints and fulfill the same number of requests. The lesson
does not claim that one solver or fairness definition is generally superior. It shows that an omitted
secondary objective leaves a real decision hidden inside an arbitrary tie.

## Fixed teaching instance

- four staff: A, B, C, D;
- three days: Monday, Tuesday, Wednesday;
- two shifts per day: day and night;
- exactly one staff member covers every shift;
- each staff member works at most one shift per day;
- a night shift forbids the following day's day shift for the same staff member;
- staff D is not qualified for night shifts;
- the request matrix is fixed and versioned;
- all `4^6 = 4096` slot assignments are inspected; 441 satisfy the hard constraints.

The canonical objective is:

```text
maximize 10 × fulfilled_requests − workload_range
```

The preference-only contrast first maximizes `fulfilled_requests` and deliberately omits
`workload_range` from its tie-break. The balanced schedule does not trade away a request in this
instance: both fulfill six requests, while workload range changes from three to one.

## Visualization contract

Analytical job: compare two schedules. Data shape: a small staff × day matrix with one categorical
assignment per cell.

The main evidence is an HTML schedule table, not a generic line chart:

- rows are staff;
- columns are days;
- each cell says `日勤`, `夜勤`, or `休`;
- a request match adds a visible `希望` label; color is redundant;
- metrics beside the table show fulfilled requests, workload range, and hard violations;
- hard-constraint checks and formulation detail stay in a disclosure below the evidence.

Color roles are limited to neutral rest cells, a primary assigned-shift accent, a secondary
request-match accent, and a separate violation color. Text and symbols carry every essential state.

## Responsive and interaction design

- At most two schedule instances appear together.
- Desktop Compare uses two equal-width small multiples.
- Mobile portrait stacks the schedules; each three-column table remains readable without horizontal
  gestures.
- Theater shows one schedule first, with constraints and provenance below it.
- No hover, drag, animation, private persistence, or remote state is required.
- Canonical URLs are the scenario and comparison routes; there is no additional view state.
- Keyboard and screen-reader users receive native table headers, cell labels, metric descriptions,
  and the full text alternative.
- Static screenshots preserve the same table, metrics, caveat, and source trail.

The renderer is React plus semantic HTML/CSS. SVG, Canvas, WebGL, and a chart dependency would add
maintenance cost without improving this 24-cell matrix.

## Comparison policy

The comparison is a parameter/tie-break sensitivity contrast:

- fixed: instance, requests, qualifications, hard constraints, candidate enumeration order, and
  4096-evaluation budget;
- changed: whether workload range participates in tie-breaking;
- synchronization: complete candidate enumeration;
- metrics: fulfilled requests, workload range, hard violations, canonical objective;
- ranking eligibility: false;
- caveat: no solver runtime, scalability, or general workforce-policy ranking.

## Deliberate non-goals

- no claim that workload range alone establishes fairness;
- no labor-law, health, safety, consent, or long-horizon guarantee;
- no absence, demand uncertainty, multi-skill coverage, or rolling re-optimization;
- no CP-SAT wall-clock or search-performance benchmark;
- no inference from the fixed four-person lesson to a production roster.

## Required proof

- evaluator rejects non-binary or hard-infeasible assignments;
- deterministic enumeration reproduces both declared schedules and all metrics;
- Python and TypeScript contracts reject identity or shape drift;
- Theater and Compare render the schedules accessibly at desktop and mobile widths;
- Case → Theater → Compare → Case remains reachable;
- journey Coverage changes from partial to complete;
- a deterministic staged release produces every public projection.
