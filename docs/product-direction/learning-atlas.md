# Product direction: 引ける辞書と、進める道筋を持つ学習アトラスへ

- Status: working product direction（`problem-first-atlas.md` の後継）
- Date: 2026-09-30
- Decision record: [ADR 0017](../adr/0017-formulation-atlas-and-learning-paths.md)

## 1. なぜ使われないのか

目標は正しい。基盤も厚い。それでも「使おう」という気持ちにならない理由を、利用者の目線で並べます。

| 利用者の気持ち | 実際のサイト | 足りないもの |
|---|---|---|
| 「二次錐計画って何？」と引きたい | 問題型は57個DBにあるが、ページもURLも標準形の式もない | **定式化の辞書** |
| 何から読めばいいか知りたい | Learn は128件の平らなカード一覧 | **順序と「次の一歩」** |
| 最適化を理解したいだけ | Home の主行動は「条件から診断」 | **学ぶための入口** |
| 読みたいのは説明 | 手法ページの冒頭に `手法ID (Method ID): M_…`、押せないボタン、読み方ガイド | **最初の視線を本文に** |
| 日本語で読みたい | `incumbentとrelaxation boundで改善不能なsubtreeを除外` | **用語の日本語化** |
| 説明を信用したい | 問題型の要約が `線形計画。変数=continuous、…`、適合理由が全行同じ定型文 | **定型文を知識として扱わない** |

要するに、**正しさを守る仕組み（ID・根拠・生成物・検証）は育ったが、理解を進める仕組み（何を・どの順で・どう書くか）が育っていなかった**のが根本原因です。

## 2. あるべき構造：骨格・肉・投影

```text
骨格（structure）          肉（lessons）                  投影（projections = アプリ）
─────────────────          ─────────────                  ─────────────────────────
問題型（定式化） 57         定式化記事（8節の型）           辞書     /formulations
  └ 関係 58本              手法記事                       コンパス  /formulations/:id
手法 105                   概念記事                       道筋     /paths
概念（feature）            動く図（explorable 1記事1つ）    診断     /diagnose
事例 35                    事例の解説                     事例     /gallery
根拠 110                                                  比較・Theater
```

- **骨格**は網羅を保証します。全要素が最初からページを持ち、欠けは「準備中」として見えます。
- **肉**は1本ずつ足します。型が決まっているので、誰が書いても同じ順で読めます。
- **投影**は骨格と肉から生成します。新しい画面は、新しい種類のデータを作らずに、既存の骨格の見せ方として作ります。

学習者の動線は2本です。

- **引く（辞書）**: 形の名前、あるいは「配分する」「外れ値」のような日常の言葉 → 定式化ページ → コンパスで隣の形へ → 手法へ。
- **進む（道筋）**: 問いの列をたどる。各ページの上に「この項の問い」、下に「次の問い」が常に出る。

どちらの動線も最終的に「自分の問題を解く」（診断・事例）へ合流します。

## 3. 育てる仕組み

コンテンツが今後も良くなり続けるために、次のループを回します。

```text
backlog（参照数で順位）→ 記事を1本（8節の型・検算済みの例）→ export が型と関係を検証
      ↑                                                            ↓
道筋に骨格の型を組み込む ←──── 辞書・コンパス・道筋に即時反映 ←────┘
```

- `scripts/formulation_backlog.py` が、道筋・事例・関係からよく参照されるのに記事がない型を上位に出します。「何を書くか」を議論で決めません。
- 道筋に骨格の型を入れると、その型は backlog の上位に上がります。道筋が執筆計画を兼ねます。
- 記事の品質は文字数ではなく、型（節の有無と順序）と、検算できる例で担保します。

## 4. 既存規則の見直し

以前の規則は「データの正しさ」を守るためのものが大半で、「読みやすさ・学びやすさ」を守る規則が弱いか、逆方向に働いていました。見直しの結果を、**変えたもの**と**次に変えるべきもの**に分けます。

### 4.1 今回変えたもの

| 以前 | 変更後 | 理由 |
|---|---|---|
| 問題型にページがない（canonical URL なし） | 全問題型が `/formulations/<id>` を持つ | 学習者の基本単位を引けるようにする |
| 概念記事の公開条件は「本文1,200字以上・目次4項目以上・次に読む1本」 | 定式化記事は **8節の型と順序** を公開条件にする | 字数は冗長さに報いる。型は読む順を保証する |
| 学習順序は各ページ脇の関係表示だけ | 問いでつないだ道筋を authored seed にし、前提の順序を export で検証 | 「次に何を読むか」を毎回読者に考えさせない |
| Home の主行動は診断と事例 | 「学ぶ」と「解く」の2入口 | 理解したい人の主行動を作る |
| 主ナビ「条件で診断・事例を見る・手法を学ぶ」 | 「道筋・辞書・手法・診断・事例」 | 学ぶ導線を先に。375px で全部見える短い名詞に |
| 手法ページ冒頭に内部ID、押せない「地図上で見る」、DB名（例: 最急降下法）と記事名（勾配降下法）の不一致 | 見出しは記事名、IDは末尾、押せないボタンは出さない | 自分たちの「最初の視線を固定する」原則に実装を合わせる |
| 教材一覧のテストが記事数（128件など）を固定値で検査 | 件数は生成データから計算し、振る舞いだけを検査 | 記事を足すたびにテストが落ちる摩擦を消す |
| AGENTS.md の冒頭がデータ保全の注意 | 冒頭を「学習者に何を届けるか」と育て方にし、保全の規則はその後へ | 入口の文書が、作るものの目的を最初に伝える |

### 4.2 次に変えるべきもの（提案）

優先度順です。どれも、この文書の構造（骨格・肉・投影）の上で小さく実行できます。

1. **手法記事にも型を与える（着手済み）。** 型「30秒でつかむ → 一手の意味 → 小さな例 → 向く条件・避ける条件 → Python → 診断値 → 失敗・切替の兆候 → 次に読む」を `content_skeletons.py` で検査し、既存記事は移行待ちリスト（縮む一方）で段階的に移す。2026-09-30 の第1陣で、主要な手法24本と family 1本を移行した（残り67本）。`method-content-density.md` の Level 0〜4 は「何が揃っているか」の棚卸しとして残すが、読む順は型が保証する。
2. **用語集を authority にして、英語混じりを機械的に減らす。** 今の言語規則は「日本語（English）を初出で併記」を文章の努力目標にしており、`step`、`solver`、`incumbent` がそのまま残る。`data/seeds/terms_ja.json`（英語 → 日本語表示、併記の要否）を作り、`prose.language-mixing` 警告を用語集に基づく検査へ置き換える。
3. **定型文をデータとして公開しない。** `problem_archetypes.summary` や `problem_method_fit.rationale` のように、列の値を並べただけの文は、知識ではなく表示用の埋め草です。`unknown is data` の原則どおり、書けない文は空にし、UI は構造化された値（記述子チップ）で示す。辞書の読み下しは seed が持つので、DB側の定型要約は表示から外せる。
4. **生成レポートをコミットしない。** `docs/content-quality-report.md` などは記事を1本足すたびに再生成が必要で、忘れるとテストが落ちる。CI の成果物にし、リポジトリには入れない。
5. **生きたデータの件数や文言をテストに書かない（残り）。** 教材一覧のテストは直した。手法記事を型へ移すと、記事の特定の文言（例: `solverの一般性能ranking`）や旧見出しを字面で検査するテストが11件落ちた。これらは「根拠のない順位を示さない」「制約違反は解ではない」のような**守るべき内容**を、文言の一致で代用している。内容の検査は、節の型と、`一般(的な)?性能(ranking|ランキング)` のような意味の目印に置き換え、表記の日本語化で壊れないようにする。
6. **journey の孤立判定に道筋を数える。** 今は Gallery 事例から辿れない記事がすべて `published_content_without_journey` の警告になる。道筋に入っている記事は孤立ではない。
7. **規則文書を減らす。** docs 直下に34文書、ADR と research が25ある。同じ規則が AGENTS.md、`adding-knowledge.md`、maintenance skill、各 skill に重複して書かれ、どれが正か読み手が迷う。規則は1か所に置き、他は参照だけにする。
8. **Map（問題構造マップ）を辞書へ統合する。** Map は「代替解法」「変数と計算資源」などの意味階層で、定式化の辞書と役割が重なる。辞書の系統とコンパスに寄せ、Map は診断の補助に絞る。
9. **定式化関係の全体図。** 57型×58関係の全体を1枚で見る図は、系統ごとの列に `special_case_of` の鎖を描く形で作れる。スマホでは系統ごとの縦の鎖に分解する。

## 5. 成功の測り方

- 骨格のみの型の数（減っていく）と、道筋に含まれる骨格の型の数（先に増え、その後減る）
- 道筋の完走に必要な記事が揃っている道筋の数
- 定式化ページから手法ページ、手法ページから定式化ページへの往復の数（関係の役立ち度）
- 総ページ数や総文字数は成功指標にしない
