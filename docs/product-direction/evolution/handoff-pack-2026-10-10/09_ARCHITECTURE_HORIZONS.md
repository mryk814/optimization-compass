# 9. GitHub Pagesの制約を外すと何が可能か

## 静的サイトでもできることを過小評価しない

GitHub Pagesは静的ファイルの配信基盤だが、クライアントのJavaScript計算、WebGL、Worker、WASMまで禁止するものではない。関係探索、学習状態、短い数値実験、操作図・動画連携の多くは今の配信形態で試せる。PyodideやJupyterLiteはブラウザ内計算の候補になる。[E33,E35,E36]

制約は長時間のnative solver、秘密鍵、持続的な利用者DB、サーバー側認証/共同編集、queueと課金管理などに現れる。そこだけを別層にする。

## 四層の発展経路

|段階|利用者の価値|追加する境界|進む条件|
|---|---|---|---|
|A 静的Atlas|辞書・学習・地図・検証済みtoy|今の正本と生成物|初期の主戦場|
|B ブラウザ実験室|入力を変えた小さな再計算|Worker/メモリ/中断/バンドル分離|定型toyだけでは学習課題が解けない|
|C ローカルcompanion|私有データとnative solverへ接続|allowlist runner、入出力、時間/容量制限|現実の評価契約を再現する需要が確認された|
|D hosted workspace|複数人の前提/結果/判断の共有|認証、権限、queue、費用、監査、保存|継続利用と共同作業の価値が実測された|

Bは通常の本文を重くしない。Pyodideの一部割込みにはSharedArrayBuffer等の条件が関わるため、配信条件の確認とWorker終了による代替を用意する。ブラウザにすべてのnative solverを移せるとは仮定しない。[E34]

Cは任意のshell実行窓ではない。ユーザーが承認した評価器IDとschemaを通し、timeout・メモリ・出力サイズ・作業ディレクトリを制限する。失敗を数値に混ぜずstatusとして保持する。作業データは知識DBの正本と別に置く。

Dは最初から作らない。利用者が理解に詰まっている問題を、アカウント・課金・多人数機能では解けない場合が多い。技術的に可能なことと価値があることを分けてゲートを置く。

## 人間とAIが同じ対象を扱う

共有するのは画面のピクセルでなく、問題、条件、選択手法、情報の確定状態、根拠、実行設定、生成物の版。人間は図と表、AIは同じstateのJSONを見る。AIが提案した定式化とユーザーが確定した定式化は別の状態にする。

既存read-only guidance境界を使い、外部AIへbriefを出すのが最小の接続である。MCPを導入する場合もthin adapterとし、推薦・除外・unknown・source IDsを改変しない。MCP transportは現在のADRで後続扱いである。[R11]

## 安全・再現性

数式文字列をevalしない。source proseやagent入力は命令でなくデータ。公開された資料に含まれる指示でツール権限を変更しない。任意URL取得はSSRF境界、MarkdownはXSS境界、実行器はCPU/メモリ/ファイル境界を持つ。秘密鍵を静的bundleへ入れない。

モデルの設定、入力hash、solver版、seed、budget、status、残差、保証範囲を結果に残す。最適化の成功を、物理実験の安全や意思決定の正当性と同一視しない。
